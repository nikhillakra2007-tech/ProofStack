# 7. AI pipeline

The model has exactly three jobs: propose competing hypotheses, propose a minimal patch, and revise a patch against a reproduced counterexample. It never runs code, measures, or decides. The client, resolver and prompt renderer below are the tested reference implementation (`tests/test_llm.py` runs them against a local stub of the API).

## 7.1 Nebius Token Factory client configuration

| Item | Value |
|---|---|
| Base URL | `https://api.tokenfactory.nebius.com/v1` (OpenAI-compatible; override with `NEBIUS_BASE_URL`) |
| Auth | `Authorization: Bearer $NEBIUS_API_KEY`; the key is held by the controller only |
| Catalog | `GET /v1/models`; resolved once per run and pinned in `models.lock.json` |
| Endpoint | `POST /v1/chat/completions` |
| SDK | The OpenAI Python SDK works with `base_url` set and `max_retries=0`; the reference client is stdlib so the retry policy below is ours alone |

### 7.1.1 Model routing and ID reconciliation

Routes: diagnosis (reasoning model), patch (fast model), feedback (same as patch). The specified preferences are `nvidia/nemotron-3-super-120b` for diagnosis and `nvidia/nemotron-3.5-lightning` for fast patch loops.

**Reconciliation note (observed 13 Oct 2026).** Nebius announced Nemotron 3 Super on Token Factory, and third-party gateway catalogs that mirror the Token Factory list show that model as `nvidia/nemotron-3-super-120b-a12b` (with the `-a12b` suffix). No listing for `nemotron-3.5-lightning` was found; a Nano-class Nemotron model appears under `nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B`. These sources are not Nebius's own catalog, so the resolver, not this document, is authoritative: model IDs are resolved against the live `GET /v1/models` at start-up and a request for an unavailable ID fails closed (exit 3) listing the nearest NVIDIA IDs. The two preferences are kept as the configured *requests*; the resolved IDs are what the ledger records.

Resolution order: exact match; case-insensitive match; unique prefix (so `nvidia/nemotron-3-super-120b` resolves to the `-a12b` ID if and only if that is the only catalog ID with that prefix); first present fallback; otherwise error. An ambiguous prefix is an error.

```yaml
# proofstack.models.yaml  (committed; models.lock.json is generated by `proofstack doctor --check models`)
routes:
  diagnosis:
    prefer: "nvidia/nemotron-3-super-120b"
    fallbacks: ["nvidia/nemotron-3-super-120b-a12b"]
    temperature: 0.3          # some diversity across the competing hypotheses, stable JSON
    top_p: 0.9
    max_tokens: 6000          # reasoning tokens count toward this on most reasoning models
    read_timeout_s: 120
    extra_body: {}            # reasoning on/off or budget keys: bind from the model card at doctor time
  patch:
    prefer: "nvidia/nemotron-3.5-lightning"
    fallbacks: ["nvidia/NVIDIA-Nemotron-3-Nano-30B-A3B", "nvidia/nemotron-3-super-120b-a12b"]
    temperature: 0.1
    top_p: 0.9
    max_tokens: 3000
    read_timeout_s: 60
    extra_body: {}
  feedback: {inherit: patch}
requirements:
  vendor_prefix: "nvidia/"    # at least one NVIDIA open model must serve a route (hackathon eligibility)
  seed: "sha256(task_id|cycle|route) mod 2**31"   # best effort; recorded even if the endpoint ignores it
```

Reasoning controls (thinking on or off, budgets) differ by model card; they are passed through `extra_body` and `doctor` records which keys the endpoint accepts. Diagnosis uses reasoning; patch and feedback do not, to keep loops fast.

### 7.1.2 Structured output, retries, timeouts

| Concern | Policy |
|---|---|
| Output format ladder | 1) `response_format = {"type": "json_schema", "json_schema": {name, strict: true, schema}}` where the model supports it; 2) `{"type": "json_object"}` (the guaranteed floor). The first HTTP 400/422 mentioning `response_format` or the schema downgrades that model for the rest of the run |
| Local validation | Always. Every response is parsed and validated against its JSON Schema regardless of format used |
| Repair | At most 2 repair turns per call: the invalid reply and the validator errors are appended; still invalid, `INCONCLUSIVE` |
| 429, 500-504, timeouts | At most 3 attempts; honour `Retry-After`, else full jitter `uniform(0, min(20, 2**k))` seconds |
| Refusal, `finish_reason=length` | Not retried silently; the call fails and the run ends `INCONCLUSIVE` with the reason |
| Timeouts | Connect 10 s; read 120 s (diagnosis), 60 s (patch, feedback) |
| Budget | Sum of `usage` tokens across calls is checked before every call; exhaustion ends the run `INCONCLUSIVE` |
| Recording | Per call: route, requested and resolved model id, resolution kind, tokens in and out, latency, attempts, repairs, format used, SHA-256 of prompt and response; full texts stored as artifacts |

## 7.3 Context packs

Each problem in the catalog defines a context pack: `ast_slice`, `runtime_evidence`, `invariants`, `forbidden`, `fix_shape`. The controller assembles it, the model never builds its own evidence. Assembly rules:

1. `ast_slice` is the enclosing function plus at most 10 lines of context, line-numbered, taken from the baseline worktree by `ast` (not by the model), wrapped by `fence()`.
2. `runtime_evidence` is copied from the probe's `Finding.metrics` and `evidence`; secret values are never included (P13 carries digests).
3. `invariants` and `forbidden` come from the catalog entry and the task's `correctness` section; they are never trimmed.
4. If the prompt exceeds the context budget, drop in order: unrelated imports, docstrings, distant helper functions. Never drop invariants, forbidden moves, or the flagged lines.
5. Patch size limits (`max_diff_lines`, `max_files`) and protected paths are stated in the prompt and enforced by gate G0 regardless.

Counterexample record built by the controller from the probe's evidence (truncated to 2,000 characters, secrets redacted):

```json
{"gate_id": "P03", "probe_id": "P03", "family": "SEC", "kind": "exploit",
 "steps": [{"n": 1, "who": "alice", "op": "get_object(1)", "result": "200 owner=alice"},
           {"n": 2, "who": "bob", "op": "get_object(1)", "result": "200 owner=alice  <-- must be denied"}],
 "minimal_input": {"owners": {"alice": 1, "bob": 2}}, "fingerprint": "7b1c0e94d2a65f38"}
```

Kinds: `exploit` (probe trace), `growth` (sizes and times), `state` (interleaving seed and final state), `diff-mismatch` (input, baseline output, candidate output), `test-failure` (test id and assertion message).

## 7.5 Safety and failure handling

| Risk or failure | Handling |
|---|---|
| Prompt injection in repository text, comments, logs | Fenced as data; system rule 2; the model's output cannot cause execution, only a diff that must pass G0 and every gate |
| Model proposes a command | Only catalog experiment ids are accepted; argv is built by the controller from a fixed template |
| Patch touches tests, benchmarks, policy | G0 compares protected-path hashes before and after; any change is `REJECTED` |
| Patch too large or off-target | `git apply --check`, line and file limits; a repair cycle is spent |
| Hypotheses indistinguishable | Selector returns no experiment; run ends `INCONCLUSIVE` ("indistinguishable") with the matrix recorded |
| Invalid JSON, schema violation | Up to 2 repairs, then `INCONCLUSIVE` |
| 429, 5xx, timeout | Backoff policy 7.1.2; exhaustion ends `INCONCLUSIVE` and records the HTTP status |
| Refusal, truncation | Fail the call; never silently increase the budget |
| Model unavailable or ID unknown | `doctor` and run start fail closed, exit 3 |
| Credentials | Never in prompts or sandbox; ledger stores prompt hashes and artifact paths |

## 7.6 Determinism and audit

Probe and bootstrap seeds are fixed; model calls carry a derived `seed` and `temperature <= 0.3`; every request and response is hashed into the ledger and stored as an artifact, so a run is audited from the ledger even if the model later changes. Model output is never trusted to reproduce; the *gate results* are what reproduce.
